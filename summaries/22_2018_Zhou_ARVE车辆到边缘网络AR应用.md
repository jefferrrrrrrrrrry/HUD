## 一、研究背景与问题

2018年，加州与上海分别开放公共道路自动驾驶测试，车载ADAS（自动紧急刹车AEB、自适应巡航ACC等）已普及。但**单车感知存在物理盲区**：
- 场景1：前车突遇坑洞——后车需被通知避让（实时延迟、街道尺度）；
- 场景2：右转路上拥堵不可见——拟入路车辆需要重计算最优路径（中等延迟、城市尺度）。

现有三种通讯架构均有短板：
- **V2V（车到车）**：近距离表现好，但**城市尺度信息转发昂贵**；
- **V2C（车到云）**：传输+处理+分发的累积延迟无法满足紧急响应要求；
- **V2I（车到路侧）**：分发好，但RSU缺乏计算能力。

**实测延迟（Table I）**：通过LTE网络从手机到不同服务器的RTT：
| 目标 | RTT (ms) |
|---|---|
| Edge server | **19.9** |
| Cloud A（本地城市5 km） | 24.9 |
| Cloud B（附近国家1000 km） | 52.4 |
| Cloud C（更远2500 km） | 58.8 |

边缘服务器比最近的云快20%（5 ms），对急刹/碰撞预警的累积延迟具有决定性意义。

**核心问题**：能否设计一个**车到边缘（V2E）架构**，将计算与缓存能力部署到基站/聚合点，支持AR-HUD等带宽密集+时延敏感的车载应用？

## 二、系统设计（这是一篇工程系统论文，无人因实验）

### 2.1 系统架构（三层）

1. **设备层（Device）**：车辆、行人手机、路侧建筑等任何向ES传输数据的客户端；
2. **接入网（Access Network）**：**Tier 1 Edge Server (T1 ES)** 与基站协位部署，覆盖宏小区+小小区，提供低延迟服务；
3. **核心网（Core Network）**：**Tier 2 Edge Server (T2 ES)** 与聚合点协位，覆盖多个T1区域，提供大规模数据汇总（如全市交通流优化）；
4. **可选云层（Cloud）**：按需备份与历史数据存储。

### 2.2 六步通讯流程

① **邻居通知**：检测设备将原始报告（图像帧、坐标、速度、运动方向）以低压缩发往最近T1 ES → ② **数据处理**：T1 ES通过机器学习提取信息，与本地实时地图匹配（绝对坐标映射）→ ③ **数据传输**：根据规则向邻近T1 ES传播 → ④ **数据分发**：通知附近车辆/行人 → ⑤ **数据聚合**：T1向T2汇总（如多街区洪水）→ ⑥ **数据上传**：T1/T2与云同步，云用于备份与政策推演。

### 2.3 ES服务架构（四平面）

- **Device Service**：设备发现（基于"HELLO"包模型，订阅式）、注册（生成UID与设备profile）、通讯（UDP用于低延迟图像传输）；
- **Data Management**：Device Data、Meta Data、Event Data（带Timestamp/Coordinates/Type/Data/Device ID字段的事件库）、Machine Learning（图像帧分析，本工作集成YOLOv3物体检测）；
- **Operation**：Rules（生成规则）、Notification（向客户端发警报）；
- **Export**：Client Registration（邻近ES注册）、Distribution（数据导出/备份）。

### 2.4 应用：View Share（视角共享）

具体的AR-HUD应用：客户端周期性上传{相机图像, GPS, 朝向, 时间戳, IP}到ES → ES用YOLOv3做物体检测 → 计算每个检测到目标的GPS（先做鸟瞰透视变换，从像素位置转换为实地米位置）→ 将{时间戳, 物体名称, 物体GPS}返回客户端 → 客户端以AR方式在屏幕上叠加，**让驾驶员看到被前车遮挡的目标**。

### 2.5 隐私与安全

- V2V直接通讯会暴露车辆移动模式；
- ARVE中ES作为中介，**移除原始发送者的私有信息**后再分发，保护隐私同时确保信任；
- 订阅机制保证仅信任服务的用户参与。

## 三、关键指标与测量

### 3.1 实现细节

- **客户端**：Android平台、Xiaomi Mi5（高通骁龙820四核2.15GHz, 4GB内存）+ OpenGL渲染。
- **ES**：Linux PC，i7-5820K六核, 64GB内存, **NVIDIA GTX 1080Ti GPU**，类似中价位2018年边缘服务器。
- **云**：Google Cloud实例（6 vCPU, 16GB内存, NVIDIA K80 GPU）。
- **物体检测**：YOLOv3 (GPU实现)。
- **图像处理**：OpenCV（视角变换）。
- **ES框架**：基于EdgeX Foundry开源IoT边缘计算框架，添加UDP socket、修改Event Data为多级唯一排序数据库、集成机器学习模块。
- **测试网络**：手机→ES通过WiFi（ES作为AP）；ES→Google Cloud RTT=28.76 ms；手机→ES RTT=6.84 ms。

### 3.2 性能指标

- End-to-end latency；
- Bandwidth at device/edge/cloud；
- Scalability across traffic densities。

## 四、主要结果与发现（具体数值）

### 4.1 View Share延迟分解（Figure 7）

| 阶段 | ES (ms) | Cloud (ms) |
|---|---|---|
| Client Data Collection | 6.7 | 6.7 |
| Uplink Latency | 8.9 | 20 |
| Object Detection | 52 | 63 |
| Policy Control | 1.2 | 1.4 |
| Downlink Latency | 6.4 | 17 |
| Client Rendering | 17 | 17 |
| **总计** | **92.2** | **125.1** |

- **ES比云快32.9 ms（约20–26%）**；
- 上行+下行延迟差占主要部分（21.7 ms）。

### 4.2 城市规模扩展性（伦敦中心区数据）

研究区域：3.91 km × 5.75 km；LTE基站3,455个（81个macrocell覆盖>3000m）；分为7个流量分区。

- **峰值1小时内通过车辆**：14,494辆（6pm）；
- **每ES峰值任务量**：Nr/ES = 14494/3600 × 300 × 1 = **1200 任务/秒**；
- 单ES每秒可处理对象检测：C = 1000/52 = **19个并行任务**；
- 满足峰值平均需求所需ES数：1200/19 ≈ **64个ES**（图5）。

### 4.3 带宽对比（Table III）

| 层级 | 最小 (MB/s) | 最大 (MB/s) |
|---|---|---|
| 设备 | 0.0581 | 0.0581 |
| 边缘服务器 | 2.89 | 5.07 |
| 云服务器 | **184.9** | **324.5** |

- 峰值时段云服务器需要>2.5 Gb/s带宽，**ES方案降低98%**云端带宽，仅约40 Mb/s/基站（LTE可承载）。

### 4.4 不同部署策略（Figure 8）

- **0%（纯云）**：延迟最高；
- **100%（纯边缘）**：所有时段最低延迟，比纯云降低~32 ms；
- **80% Edge + 20% Cloud混合**：与纯边缘相似性能，成本更低；
- **40–60%混合**：性能与成本折中。

## 五、对AR-HUD时空设计的启示

**时间层面**：
- AR-HUD预警端到端延迟必须<100 ms（紧急刹车场景）。本研究证明**边缘计算可将延迟从125.1 ms降至92.2 ms**，使端到端达标；
- 对于行人/PM等高速目标，每节约5 ms都可换算成车辆减速距离（30 km/h下约4 cm，120 km/h下约16 cm）；
- 城市尺度峰值时段需要64个ES才能完全覆盖单一应用的算力需求，对运营商部署提出明确量化指标。

**平面层面**：
- View Share通过云端鸟瞰透视变换+回传，让本车AR-HUD能"看到"被前车遮挡的目标——这扩展了**AR-HUD的物理视野边界**，是单车感知无法做到的；
- 后续Honda、TUe等团队（如ARive 2025）的研究本质上仍是单车感知，未利用V2E能力——V2E是本领域下一阶段的扩展方向。

**立体层面**：本论文未涉及立体显示，主要关注通讯架构。

**适用边界**：
- 仅在LTE覆盖良好的城市环境有效；
- 4个严重晕动症事件未处理；
- 严重依赖基站部署密度；
- 隐私保护机制需要进一步优化（订阅模型对用户体验有摩擦）；
- 当应用涉及多个V2V/V2E协议混合时，规则冲突需统一调度。

## 六、本文局限性与未来工作

1. **未做人因评估**：纯工程系统论文，无驾驶员反应时间、信任、负荷等人因数据；
2. **物体检测精度未量化**：仅引用YOLOv3，未做行人/PM等细分类性能；
3. **5G/DSRC对比有限**：仅讨论LTE，未实测5G；
4. **测试规模小**：单部手机+单台ES，未在真实多车场景下规模化；
5. **隐私机制未实测**：订阅模型未做安全审计；
6. **AR渲染管线未深度优化**：仅用OpenGL基础渲染。

**未来工作**：5G + V2E结合；多种应用并发的优先级调度；规模化在地实验。

## 七、与本研究主题的关联

本论文与本研究主题的关联是**基础设施层而非感知/显示层**：

1. **延迟瓶颈的工程解决方案**：AR-HUD预警系统的端到端延迟既包括"传感→检测→显示"的车内管线，也包括"车→云→车"的车联管线。本研究主要关注车内显示部分，但车联部分（如V2X接收周边车辆/RSU数据）同样关键——ARVE提供了**将云端延迟从125 ms降至92 ms**的工程方案；

2. **View Share应用直接相关**：通过云端透视变换让本车看到被遮挡目标——这对**行人碰撞预警的盲区扩展**具有直接意义。城市常见场景如"停泊车辆后方冲出的行人"，单车感知盲区严重，V2E能融合多车视角；

3. **64个ES覆盖一个城市的工程估算**：为本研究主题的"产业化落地条件"提供具体量化——AR-HUD预警若依赖V2E增强，仅伦敦中心区一应用就需64个ES，全市规模化部署具有可行性但需运营商投入；

4. **带宽节约98%**：实际意味着AR-HUD预警在5G/LTE双制式下都可大规模并发，无需独占带宽；

5. **5+5路Honda + TUe合作模式的前奏**：ARVE论文是2018年的工程基础，**ARive 2025（idx 20）的Honda + TUe合作**正是建立在这一基础上，AR-HUD研究已从单车感知向V2X/V2E协同演进。

> **Takeaway**: Zhou et al. 2018 (ARVE/EARVE) 是车联AR-HUD的**基础设施工程论文**，量化证明了**边缘计算将AR应用延迟从125 ms降至92 ms（20%缩短）**、**带宽节约98%**、**64个ES可覆盖伦敦中心区峰值需求**。对本研究主题最重要的启示是：① AR-HUD行人预警的延迟瓶颈不仅在车内管线，也在车-云通信；② V2E能扩展单车感知的物理视野（View Share），可解决停泊车辆等盲区行人问题；③ 实际工程部署需要约64个ES/城市核心区，是产业化的关键基础设施门槛。本文是2018年工程基线，到2025年AR-HMD（ARive）的演进路径上一个重要节点。
