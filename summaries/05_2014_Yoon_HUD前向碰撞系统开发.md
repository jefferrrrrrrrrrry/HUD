## 一、研究背景与问题

HUD 在战斗机中已普及，可让飞行员无须转移视线即可获取信息。汽车 HUD 始于 1988 年通用汽车 Oldsmobile Cutlass Supreme。文献（Horrey 2003）指出 HUD 相比抬头显示（HDD）可缩短 0.2 s 反应时并提高情境感知。但现行商用 HUD 仍只显示车速、导航等简单信息，与仪表盘信息高度重合，没有充分利用 HUD 的潜力。前向碰撞预警系统（FCWS）虽已大量上市，但仅以声音报警或简单视觉符号通知驾驶员，不能直接关联到道路上的具体目标。

近年关于物体检测（HOG、SVM、深度网络）与基于 HUD 的 AR（AR-HUD）的研究兴起。后者把信息"注册"到驾驶员视野中（in-vehicle AR-HUD system displays information registered to the driver's view），能在保持视线在路上的同时叠加目标位置。然而，这一融合仍面临三大工程挑战：(1) 高精度实时检测车辆与行人；(2) 在低延迟下计算威胁等级；(3) 透过 HUD（透明显示器）正确把警示叠加到驾驶员视线坐标系中。本文目的就是构建一个端到端的"增强前向碰撞预警系统"（Augmented FCWS）：检测前方车辆/行人 → 评估 TTC 威胁等级 → 通过 HUD 显示增强警示。

本研究的可证伪命题（更偏工程）：
1. 采用"等高拼接图像（equi-height mosaicking image）"+ 1D 搜索 HOG-SVM 分类器，可在保持精度的前提下大幅缩短检测时间（相对 OpenCV GPU-SVM）；
2. 通过 2D 单应性（homography）+ 眼动仪实时补偿，可在 HUD 上正确注册警示图形。

## 二、研究方法

本文是"工程系统开发 + 性能基准评估"型研究，无被试用户实验。

### 2.1 被试与样本
- 论文未明确报告。被试不是本研究核心；评估对象是检测算法性能与系统响应。

### 2.2 实验设计
- 设计类型：算法性能对照（提出方法 vs. 基线 OpenCV GPU-SVM）；
- 自变量：算法（2 水平）× 检测目标（3 水平：高速公路车辆、城区车辆、城区行人）；
- 因变量：检测时间（ms）、精度（Precision）、召回率（Recall）、F1 measure（%）。

### 2.3 实验材料与设备
- **立体相机**：8 mm 摄像头，分辨率 640 × 480，帧率 30 fps，安装在实验车顶；
- **HUD**：使用 22 英寸三星透明 LCD 显示器（透明度 15%）作为 HUD 原型，放置在副驾前；
- **眼动仪**：用于实时获取驾驶员眼位，以动态校正单应性变换；
- **算法**：
  - 检测：等高拼接图像 + 1D 搜索 SVM 分类器 + HOG 特征 + 邻域追踪 + 非极大值抑制；
  - 校准：相机畸变、图像歪斜补偿、消失点与水平线检测；
  - 训练集：车辆正样本 1,067 张 / 负样本 38,253 张；行人正样本 7,248 张 / 负样本 27,135 张；
- **威胁评估**：
  - 距离：立体视觉获取目标距离；
  - 速度：来自车速表；
  - TTC = 距离 / 车速；
  - 威胁等级分为 3 档（具体阈值未给出）；
- **AR 注册**：
  - 车辆坐标系：原点车尾、x 轴前向、y 轴左向、z 轴右手系；
  - 2D 单应性（homography）做相机与 HUD 的几何映射；
  - 眼动仪实时校正驾驶员眼位漂移。

### 2.4 任务与流程
- 工程实验，无被试任务；
- 实际道路测试，在高速公路与市区分别检测车辆与行人；
- 用户可选"检测车辆或行人"模式实时处理；
- 视觉属性可在线调试以测试不同效果。

## 三、关键指标与测量
- 检测时间（ms）
- 精度（Precision %）
- 召回率（Recall %）
- F1 measure（%）

## 四、主要结果与发现

### 1) 车辆检测（高速公路）
- OpenCV GPU-SVM：472 ms、P = 82.14%、R = 80.20%、F1 = 81.16%；
- 提出方法：47 ms（提速约 10×）、P = 88.34%、R = 85.21%、F1 = 86.75%。

### 2) 车辆检测（市区）
- OpenCV GPU-SVM：497 ms、P = 78.92%、R = 78.23%、F1 = 78.57%；
- 提出方法：58 ms（提速约 8.6×）、P = 86.25%、R = 83.67%、F1 = 84.95%。

### 3) 行人检测（市区）
- OpenCV GPU-SVM：348 ms、P = 77.48%、R = 72.26%、F1 = 74.28%；
- 提出方法：83 ms（提速约 4.2×）、P = 88.17%、R = 80.52%、F1 = 84.17%。

### 4) 道路实测观察
- 当检测目标快速通过或车辆快速转弯时，AR 警示会延迟，需进一步提升鲁棒性；
- 透明 LCD 在透明度 15% 下可叠加 AR 图形；
- 但**透明 LCD 会引发重影（双像、diplopia）**，导致频繁的眼调节，造成眼疲劳。

### 5) 视觉属性配置
- 视觉属性包括：威胁等级、形状、颜色、透明度、相对位置和大小、图标、文字；
- 这些属性根据 TTC 自动调整；
- 具体颜色/形状参数引用 Park & Kim（2013）的可行性研究，本论文未明确列出。

## 五、对AR-HUD时空设计的启示

### 时间元素
- TTC 是核心触发参数；
- 系统将 TTC 离散化为 3 个威胁等级（具体阈值未给出）；
- 检测延迟需 < 100 ms 才能满足实时显示；
- 高速/转弯下的延迟问题揭示了"算法实时性"是 AR 警示时间设计的硬约束。

### 空间元素（平面）
- 视觉属性包含 8 类：威胁等级、形状、颜色、透明度、相对位置和大小、图标、文字；
- 警示根据 TTC 等级动态调整外观；
- 论文未给出具体颜色 RGB；
- 透明度对应透明 LCD 的 15% 设定；
- 警示与目标物保持空间对齐（路面/物体锁定）。

### 空间元素（立体）
- 22 英寸透明 LCD 模拟 HUD，作为原型；
- 注册方法：2D 单应性 + 眼动仪实时校正；
- 坐标系：车辆中心化，原点车尾，x 轴前向；
- 透明 LCD 的双像问题暗示真正量产 AR-HUD 需用投影式 HUD（论文已明确提及后续要换为投影 HUD）；
- AR 警示遮挡视野是工程瓶颈，需要最小化且智能化显示。

### 设计原则与适用边界
- "信息量必须最小化"以减少认知/视觉负荷；
- 适用：实时 GPU 平台下的城区/高速道路检测；
- 不适用：高速移动或快速转向场景（当前算法响应不足）；
- 未来需移植到车载嵌入式平台。

## 六、本文局限性与未来工作
作者明确指出：
- 当前依赖 GPU 加速计算机，与汽车工业标准嵌入式不兼容；
- 透明 LCD 在双像/眼疲劳上不可接受，需替换为投影 HUD；
- 投影 HUD 需要"有理函数模型"等处理曲面挡风玻璃畸变；
- 警示会遮挡驾驶员视野，需"基于情境感知"动态选择信息；
- 当目标移动过快或转弯过急时系统响应滞后；
- 项目处于 5 年计划（2012–2016）的第二年（即仍在原型阶段）。

未涉及方向：
- 没有用户实验验证 AR 警示的人因效益；
- 没有量化具体颜色/形状/字号的视觉显著性；
- 没有给出 TTC 阈值的具体数值；
- 没有讨论夜间、低光照、雨雾等场景；
- 没有多目标场景下的优先级管理。

## 七、与本研究主题（HUD/AR-HUD行人标注的时间空间设计规范）的关联

**时间设计规范**：
- 指出 TTC 是触发警示的核心；
- 提出"3 级威胁等级"分级框架；
- 强调检测延迟 < 100 ms 的工程门槛；
- 高速/转弯下的延迟暴露了"算法实时性"在时间设计上不可忽略的边界条件。

**空间设计规范**：
- 提出视觉属性 8 维清单（威胁等级、形状、颜色、透明度、相对位置和大小、图标、文字），为后续系统化设计提供参考；
- 给出 AR 注册的工程方法：2D 单应性 + 眼动仪动态补偿；
- 提示透明 LCD 不可用于 AR-HUD 量产（双像问题），需用投影式 HUD；
- "最小化、智能化"显示原则为后续多目标场景下的优先级设计奠定方向。

> **Takeaway**：本文是 AR-HUD 行人/车辆碰撞预警系统的早期工程实现工作，提出"等高拼接图像 + 1D 搜索 HOG-SVM"将车辆/行人检测耗时从约 350–500 ms 降至 47–83 ms，并完成了立体视觉测距、TTC 评估、2D 单应性注册和眼动补偿的完整链路；虽未做用户人因实验，但为后续 AR-HUD 行人预警的工程实现与"3 级威胁分级、视觉属性 8 维"设计框架打下了基础。
